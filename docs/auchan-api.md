# API auchan.ru — подробная документация

Всё, что удалось выяснить об внутреннем JSON API auchan.ru в ходе разведки.
Разведано 11 августа 2026 года.

---

## Коротко: что важно знать перед правками

- **Категория передаётся в теле запроса**, а не в query. В query её молча
  проигнорируют и вернут весь каталог вместо категории — без ошибки. → [раздел 3](#3-список-товаров-категории)
- **Листинг отдаёт только товары в наличии.** Отсутствующие добираются через
  объединение листингов Симферополя и Москвы с последующим запросом карточки. → [раздел 6](#6-товары-не-в-наличии)
- **Цена `0` означает «нет в ассортименте региона»**, а не «бесплатно». → [раздел 6](#6-товары-не-в-наличии)
- **Есть поля-двойники**, которые присутствуют в ответе, но всегда пустые —
  например `cashbackPercent` в карточке товара (значение лежит в `cashback.percent`). → [раздел 4](#4-карточка-товара)
- **`perPage` режется до 100** без предупреждения — нужна пагинация. → [раздел 3](#3-список-товаров-категории)
- **`merchant_id` в дереве категорий — snake_case**, `merchantId` даёт 400. → [раздел 7](#7-дерево-категорий)
- **Полный обход возобновляемый**: готовые файлы категорий пропускаются, так что
  прерванный прогон можно просто перезапустить. Папка выбирается не по сегодняшней
  дате, а как самая свежая незавершённая — обход длится десятки минут и легко
  переезжает через полночь. → [раздел 11](#11-пищевой-срез)
- Темп запросов подобран так, чтобы не ловить `401` от Qrator — если поднимать
  `WORKERS`, делать это осторожно. → [раздел 9](#9-ограничения-и-вежливость)
- Если API изменится — схему запроса можно достать из клиентского бандла,
  перебором она не находится. → [раздел 10](#10-как-искать-схему-запроса-если-api-изменится)

## 1. Почему не нужен браузер

HTML-страницы сайта закрыты антибот-защитой **Qrator**. Обычный HTTP-запрос
к странице каталога получает `401` и JS-челлендж:

```html
<script src="/__qrator/qauth.js" charset="utf-8"></script>
```

Пройти его без исполнения JavaScript нельзя — то есть парсинг HTML потребовал бы
Playwright или облачный браузер вроде Browserbase.

**Но JSON API `/v3/` челленджем не закрыт.** Он отвечает `200` на обычный
`requests`/`curl` с любым User-Agent, и `robots.txt` его явно разрешает:

```
User-agent: Googlebot
User-agent: Yandex
Allow: */v3/
```

Поэтому весь проект работает на голом HTTP. Браузер нужен только для разведки
новых эндпоинтов: открыть страницу → посмотреть сетевые запросы.

Сайт построен на Next.js (App Router), каталог рендерится на сервере, поэтому
при скролле категории XHR-подгрузки нет — пагинация обычная, `?page=2`.

## 2. Регион и магазин

Базовый URL: `https://www.auchan.ru/v3`

```
GET /v3/regions/?need_ll=1     → {regions: [...], regionDefault}
GET /v3/shops/?regionId=9      → {shops: [...], services}
```

| | значение |
|---|---|
| регион Крым | `regionId = 9` |
| **АШАН Симферополь** | **`merchantId = 729`** |
| Москва (для сравнения) | `merchantId = 3` |

В Крыму всего один магазин, поэтому `merchantId=729` однозначно задаёт Симферополь.
Ассортимент реально региональный: в категории «Молоко» Москва отдаёт 124 товара,
Симферополь — 60, причём 39 позиций есть только в Симферополе.

## 3. Список товаров категории

```http
POST /v3/catalog/products/?merchantId=729&page=1&perPage=100
Content-Type: application/json

{"filter": {"category": "moloko"}}
```

Ответ: `{items: [...], range: <всего>, minPrice, maxPrice}`

### Подводные камни

**Категория задаётся только в теле запроса.** В query-строке `categoryCode`
молча игнорируется — вернётся весь каталог (~50 000 SKU) вместо категории.
Ошибки при этом не будет, что делает промах незаметным.

**`merchantId` обязателен** — без него `400`.

**`perPage` жёстко режется до 100.** Просьба о 200 вернёт 100 без предупреждения,
поэтому нужна пагинация по `page`, пока не наберётся `range`.

**Листинг отдаёт только товары в наличии** у этого мерчанта. Позиции с нулевым
остатком в выдачу не попадают вообще — см. раздел 6.

`filter` принимает и другие ключи (они же коды из `/catalog/filter/`):
`price`, `promo_only`, `high_rating`, `brand`.

## 4. Карточка товара

```http
GET /v3/catalog/product-detail/?code=<slug>&merchantId=729
```

`code` — слаг из URL товара: `https://www.auchan.ru/product/<code>/`

Отдаёт заметно больше листинга:

| поле | что внутри |
|---|---|
| `characteristics[]` | ~23 пары title/value: **Состав**, Масса нетто/брутто, Производитель, Страна производства, Срок хранения, Температурный режим, габариты, жирность |
| `energy_value` | **КБЖУ**: `calories`, `proteins`, `fats`, `carbohydrates` на 100 г |
| `description.content` | текстовое описание |
| `rate` | `rating`, `reviews_qnt` + разбивка `rate1`…`rate5` |
| `stock` | `qty`, `storeId`, `not_available` |
| `discount` | размер скидки и её даты |
| `cashback` | кэшбэк баллами |
| `gluings[]` | другие фасовки того же товара |

Заполняемость на практике (161 товар категории «Молоко»): состав, масса, бренд,
производитель, страна, срок хранения, КБЖУ, описание, изображения, артикул — **100%**.

### Поля-двойники: где легко ошибиться

Одни и те же данные называются по-разному в листинге и в карточке, и «лишнее»
поле присутствует, но всегда пустое:

| данные | в листинге | в `product-detail` |
|---|---|---|
| процент кэшбэка | `cashbackPercent` = 5 | `cashbackPercent` = **null**, значение в `cashback.percent` |
| процент скидки | `discountPercent` | `discount.size` |
| рейтинг | `rating` | `rate.rating` |

Именно на этом парсер сначала терял кэшбэк: поле `cashbackPercent` существует
в ответе карточки, но всегда `null`.

### Кэшбэк ≠ скидка

Это две независимые механики, могут быть по отдельности или вместе:

```json
"cashback": {"point": null, "percent": 5, "limit_type": "шт", "limit": 0, "is_delayed": false}
```

Кэшбэк — баллы лояльности (золотая монетка на карточке), цена в чеке не меняется.
Скидка — это `discount.size` и перечёркнутая цена. В категории «Молоко» кэшбэк
оказался только у товаров собственных марок Ашана (бейдж `private_label`).

Бейджи в `badges[]`: `discount`, `cashback`, `private_label` («Наша марка -
создано АШАН»), `first_price`.

## 5. Отзывы

```http
POST /v3/reviews/reviews/
Content-Type: application/json

{"code": "<slug>", "pagination": {"type": "offset", "limit": 100, "offset": 0}}
```

Ответ: `{data: {qnt, reviews[], has_images, sort}, meta: {pagination: {total}}}`

**Пагинация работает только вложенным объектом `pagination`.** Плоские `limit`/
`offset`/`page` и любые query-параметры игнорируются — API молча вернёт первые
10 отзывов с `offset: 0`. Схему видно в клиентском чанке по строке
`f="reviews",m="/reviews/"`.

В отзыве: `user_name`, `created_at`, `rate`, `text`, `trigger_words` (теги вроде
«Качество», «Вкус»), `images[]`, `comments[]` — ответы поддержки Ашана.

Часть отзывов приходит с пустым `text`: человек поставил звёзды и выбрал теги,
ничего не написав. Теги в этом случае сохраняются.

Объём: 160 товаров категории «Молоко» дали 5826 отзывов и 4.5 МБ JSON.
На весь каталог экстраполируется в 1.5+ млн отзывов и ~1.5 ГБ.

## 6. Товары не в наличии

Листинг категории возвращает **только доступные** позиции. Чтобы получить и
отсутствующие, применяется обход:

1. коды товаров собираются объединением листингов нескольких мерчантов —
   Симферополь (729) и Москва (3, самый широкий ассортимент);
2. карточка каждого кода запрашивается уже под `merchantId=729`.

Так по категории «Молоко» вместо 60 позиций получается 161:

| | шт |
|---|---|
| в наличии сейчас | 60 |
| нет в наличии, но продаётся в Симферополе | 50 |
| нет в ассортименте региона | 51 |

Для последней группы **API отдаёт `price.value = 0`** — это означает «цены для
этого магазина нет», а не «бесплатно». Парсер пишет здесь `null` и ставит
`sold_in_region: false`. Характеристики, состав и КБЖУ у таких товаров есть.

## 7. Дерево категорий

```http
GET /v3/categories/?merchant_id=729&active_only=1&show_hidden=1
```

**Параметр в snake_case.** `merchantId` вернёт `400 "required merchant id"`,
хотя параметр вроде бы передан — сообщение об ошибке сбивает с толку.

Ответ ~4 МБ: 128 корневых узлов, вложенность через `items`, у каждого узла
`productsCount` и `activeProductsCount`.

### Как отличить настоящую категорию от подборки

Признак — флаг **`hiddenMenu`**:

| | корневых | листовых | товаров |
|---|---|---|---|
| `hiddenMenu: false` — меню каталога | 49 | 1576 | ~48 800 |
| всё дерево целиком | 128 | 5628 | ~245 000 |

Разница — маркетинговые подборки («Коллекции» с 2570 листьями, «Чёрная пятница»,
«Масленица») и B2B-разделы («Продукты оптом», «Гостиницам и отелям», «Ресторанам
и кафе»). Они собраны из тех же SKU, поэтому сумма по всем категориям даёт
245 тысяч строк при примерно 50 тысячах уникальных товаров — пятикратное
дублирование.

## 8. Прочие эндпоинты

| эндпоинт | назначение |
|---|---|
| `GET /v3/catalog/filter/?categoryCode=<code>&merchantId=729` | фильтры категории: бренды со счётчиками, диапазон цен. Здесь `categoryCode` в query как раз работает |
| `POST /v3/shelves/` | подборки на главной |
| `GET /v3/content/informers/` | информеры |
| `POST /v3/catalog/get-products/` | батч по артикулам |
| `POST /v3/catalog/order-fields/` | варианты сортировки |
| `GET /v3/greeting/onboardings/` | онбординг |

Мёртвое: `/v1/catalog/products` (использован в публичном репозитории
[farukhrzaev/my_parser](https://github.com/farukhrzaev/my_parser)) — сейчас `404`.
Структура тела запроса там совпадает с актуальной `/v3/`.

## 9. Ограничения и вежливость

Qrator стоит перед всем доменом, включая API. При слишком высоком темпе он может
начать отдавать `401` и на `/v3/` — парсер распознаёт это и сообщает явно,
вместо того чтобы молча писать битые данные.

Рабочие настройки, на которых проблем не возникало: **6 потоков** и пауза
**0.15 с** между запросами внутри потока (`WORKERS` и `THROTTLE` в
`auchan_parser.py`). Это даёт около 9 товаров в секунду. Плюс ретраи с
экспоненциальной паузой на `429` и `5xx`.

Если поймали `401` — снизьте `WORKERS`, увеличьте `THROTTLE` и перезапустите:
полный обход возобновляемый, готовые категории пропускаются.

## 10. Как искать схему запроса, если API изменится

Параметры многих эндпоинтов передаются в теле и не угадываются перебором. Рабочий
способ — достать схему из клиентского бандла:

1. открыть нужную страницу в браузере, собрать список чанков:
   `performance.getEntriesByType('resource').map(e => e.name).filter(n => n.includes('/chunks/'))`
2. скачать чанки и грепнуть по имени эндпоинта — например `catalog/products`
   или `reviews/reviews`;
3. рядом будет видно, что уходит в `data`, а что в `params`.

Так была найдена схема `{filter: {category}}` и вложенная `pagination` у отзывов.

## 11. Пищевой срез

API не помечает категории как продуктовые, поэтому список пришлось выводить из
данных: по полной выгрузке для каждого корневого раздела посчитана доля товаров
с заполненным КБЖУ.

Граница получилась однозначной — промежуточных значений почти нет:

| доля с КБЖУ | разделы |
|---|---|
| 88–100% | Молочные, Птица и мясо, Рыба, Сыр, Овощи и фрукты, Замороженные, Колбасные, Готовая еда, Хлеб, Бакалея, Сладости, Снеки, Алкоголь (97%), Фермерские, Собственное производство, Здоровый выбор, Настоящая Азия, Сокровища России, Вода и соки (74%) |
| 0% | Автотовары, Электроника, Одежда, Кухня, Красота и гигиена, Книги, Игрушки, Мебель, Сад и огород, Бытовая химия |

Исключены сознательно, хотя формально примыкают к еде: **«Чай, кофе, горячие
напитки»** (52% с КБЖУ — заварка и зёрна) и **«Спортивное питание и БАДы»**
(65% — добавки, а не продукты). Итого в срезе 19 разделов, список — в
`FOOD_ROOTS` (`parse_food.py`).

Алкоголь вынесен под флаг `--no-alcohol`: формально это продуктовый раздел
(97% с КБЖУ), но исключать его требуется часто.

Срез доступен в двух раскладках: `parse_food_categories.py` — файл на категорию
в `output/food-ГГГГ-ММ-ДД/`, `parse_food.py` — всё одним файлом с дедупликацией
по SKU.
