# Парсер каталога АШАН — Симферополь

Выгрузка каталога auchan.ru в JSON по магазину **АШАН Симферополь**
(`merchantId=729`, регион Крым `regionId=9`).

## Скрипты

| файл | охват | раскладка |
|---|---|---|
| [auchan_parser.py](auchan_parser.py) | одна категория | один файл |
| [parse_all_categories.py](parse_all_categories.py) | весь каталог | файл на категорию |
| [parse_food_categories.py](parse_food_categories.py) | только пищевые | файл на категорию |
| [parse_food.py](parse_food.py) | только пищевые | всё одним файлом |
| [export_parquet.py](export_parquet.py) | — | конвертация выгрузки в Parquet |
| [snapshot_prices.py](snapshot_prices.py) | пищевые, только цены | один Parquet за день |

```bash
python auchan_parser.py moloko                     # одна категория
python parse_food.py --from-dir output/ГГГГ-ММ-ДД  # пищевой срез из готовой выгрузки
python parse_all_categories.py --reviews           # + тексты отзывов (долго и тяжело)
python export_parquet.py output/food-ГГГГ-ММ-ДД    # Parquet для анализа
python snapshot_prices.py                          # снимок цен за сегодня (~30 сек)
```

**Снимок цен против полного среза.** Полный обход дёргает карточку каждого
товара (19 тысяч GET, ~19 мин) ради состава, КБЖУ и характеристик — а они
неделями не меняются. Цена, скидка с датами и остаток лежат уже в листинге
категории, поэтому ежедневный снимок обходится одним POST на страницу
категории: ~30 секунд и 250 КБ на весь пищевой каталог. Отсюда разделение:
снимок — ежедневно, полный срез — раз в неделю.

Оговорка: листинг возвращает **только товары в наличии**, поэтому в снимке
их меньше (13 тыс. против 19 тыс.). Отсутствие кода в снимке и означает
«в этот день товара не было» — товары не в наличии добираются только полным
срезом (обход кодов через мерчанта Москвы, см. `docs/auchan-api.md`, §6).

Куда пишется результат:

| скрипт | путь |
|---|---|
| `auchan_parser.py` | `output/<категория>_simferopol.json.gz` |
| `parse_all_categories.py` | `output/ГГГГ-ММ-ДД/<категория>.json.gz` + `_manifest.json` |
| `parse_food_categories.py` | `output/food-ГГГГ-ММ-ДД/<категория>.json.gz` + `_manifest.json` |
| `parse_food.py` | `output/food_simferopol_ГГГГ-ММ-ДД.json.gz` |
| `snapshot_prices.py` | `output/snapshots/ГГГГ-ММ-ДД.parquet` — **единственное, что хранится в git** |

Выгрузки сжимаются gzip'ом (примерно в 8 раз). Старые несжатые `.json`
читаются всеми скриптами по-прежнему. Для анализа удобнее Parquet —
он ещё в 10 раз меньше исходного JSON и читается по колонкам.

Пищевой срез — 19 продуктовых разделов каталога, список в `FOOD_ROOTS`
(`parse_food.py`), алкоголь отключается флагом `--no-alcohol`.

Полный обход возобновляемый: прерванный прогон продолжается с той же точки,
даже если за это время сменилась дата.

Зависимости: `pip install -r requirements.txt` (парсерам нужен только
`requests`, снимку и Parquet — ещё `pandas` и `pyarrow`).

## Автоматический сбор (GitHub Actions)

Историю цен нельзя добрать задним числом: API отдаёт только цену «на сейчас»,
пропущенный день теряется навсегда. Поэтому сбор вынесен в облако и не зависит
от того, включён ли ПК.

| workflow | когда | что делает |
|---|---|---|
| [snapshot.yml](.github/workflows/snapshot.yml) | ежедневно 07:00 MSK | `snapshot_prices.py` → коммит `output/snapshots/ГГГГ-ММ-ДД.parquet` |
| [weekly-full.yml](.github/workflows/weekly-full.yml) | понедельник 03:00 MSK | полный пищевой срез → Parquet → `web/data/` артефактом |

Расход на бесплатном тарифе приватного репозитория (2000 мин/мес): снимок
~2 мин × 30 + полный срез ~30 мин × 4 ≈ **180 минут**. Полный каталог
в облаке не гоняется — только локально, по необходимости.

Подводные камни:

- Гео-блока нет — API отвечает на запросы из зарубежных дата-центров
  (проверено на `/v3/shops/` и `/v3/catalog/product-detail/`).
- Крон Actions идёт по UTC и под нагрузкой опаздывает на десятки минут.
- Расписание **отключается после 60 дней без активности в репозитории**, и
  коммиты самого бота активностью не считаются. Если сбор встал — проверять
  это первым делом.

## PWA «Корзинка»

Конечная цель проекта — мобильный помощник покупок ([web/](web/), PWA):
каталог плитками-группами, поиск с оценкой состава, умные скидки (сравнение
с типичной ценой по истории), сортировка-комбинатор, список покупок с бюджетом,
любимое, чёрный список товаров и брендов.

**Текущий фронт работ — [docs/next-live-and-redesign.md](docs/next-live-and-redesign.md):**
перевод PWA на дизайн прототипа и на живую подгрузку цен вместо статики.
Там же принятые решения по хостингу и прокси.

**Перед правками web/ читать [docs/pwa-korzinka.md](docs/pwa-korzinka.md)** —
там экраны, формат данных, механики, правила кэша (поднимать версию в sw.js
при каждой правке!) и сложившийся процесс работы с субагентами.
Дизайн-док: [docs/design/design-doc.md](docs/design/design-doc.md).
Только светлая тема.

| файл | назначение |
|---|---|
| [build_site_data.py](build_site_data.py) | parquet → `web/data/` (индекс, шарды деталей, скоринг состава, история цен) |
| [update_daily.ps1](update_daily.ps1) | ежедневный цикл: парс → parquet → данные сайта → push в gh-pages |
| `web/` | статическая PWA без сборщиков, локально: `python -m http.server 8766 --directory web` (launch-конфиг `korzinka`) |
| [build_design_kit.py](build_design_kit.py) | `web/style.css` + шаблоны `app.js` → `design/`: дизайн-кит для Claude Design (24 карточки без сети + иконки-ассеты), launch-конфиг `design-kit`. Снят с текущего `web/`, то есть показывает состояние «до», а не цель |

Скоринг состава: Е-добавки по классам вредности (таблица в `build_site_data.py`),
флаги (сахар в первых 3 ингредиентах, пальма, усилители, подсластители), длина
состава; оценка абсолютная (0–100) и перцентиль внутри подкатегории (средний
ранг); «качество за рубль» = score / цена за кг. Шардинг деталей — сумма кодов
символов code % 32, формула продублирована в app.js (менять синхронно).

### Эталон дизайна — прототип из Claude Design

Основа дизайна — хендофф [design_handoff_shopping_list/](design_handoff_shopping_list/)
(до него ориентиром была Яндекс Лавка; исследования в `docs/design-research/`
оставлены как история решений):

| файл | что внутри |
|---|---|
| `DESIGN_SYSTEM.md` | токены, типографика, сетка, радиусы, тени, движение, тон текста |
| `README.md` | пять экранов и три шторки, механики и тексты состояний |
| `Прототип.dc.html` | живой макет, `support.js` — его логика |
| `android-frame.jsx` | рамка устройства для съёмки экранов |

Цвета, типографика, отступы, радиусы и тайминги там **финальные, воспроизводить
точно**. Фото товаров и плиток — серые заглушки `#F5F4F2`, данные
демонстрационные.

Прототип расходится с текущим `web/`; при правках побеждает прототип:

| | сейчас в web/ | прототип |
|---|---|---|
| оценка состава | число 0–100, три цвета | буква A–E, отдельная пятицветная шкала |
| гарнитура | Inter / системная | Golos Text 400–800 |
| вкладка | «Любимое» | «Избранное» |
| исключения | только скрывать | скрывать **или** помечать |
| онбординг | нет | есть |
| движение | почти нет | три скорости, каскады, пружины в микрособытиях |

## Как это работает

Данные берутся из внутреннего JSON API сайта `/v3/` обычными HTTP-запросами.
**Браузер не нужен** и в зависимостях его нет: HTML сайта закрыт защитой Qrator,
а API — нет, и он разрешён в `robots.txt`.

По каждому товару собирается всё, что отдаёт API: цены и скидки, наличие, бренд,
состав, масса, КБЖУ, все характеристики, описание, изображения, кэшбэк, рейтинг
с разбивкой по звёздам и при необходимости сами отзывы.

## Зачем это всё

Проект нацелен на **наблюдение во времени**, а не разовый срез. Пищевые
категории собираются ежедневно, весь каталог — раз в неделю. Что с этими
данными делать — в [docs/analysis-ideas.md](docs/analysis-ideas.md).
